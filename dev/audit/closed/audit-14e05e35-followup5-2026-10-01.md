## 4.0 Findings

### 4.1 Low

**F5-01 A workspace prompt path that is not a regular file runs untracked.**
- Evidence: `_task_bytes` is read only when `os.path.isfile(args.task)` is true (`orchestrator.py:2420-2422`). `is_tracked_task` returns false when the path is not a regular file (`stages.py:323-326`), so `_tracked` is false (`:2423`). The pre-run check is skipped. The `elif` branch prints "prompt is outside ai/workspace/ — not tracked" (`:2436-2438`), and the run continues with the path string as task text and `write_scope None`. The earlier existence check (`:2381`) uses `os.path.exists`, which is true for a directory or a FIFO.
- E-3h, E-3i: the approved prompt path is a directory or a FIFO at launch. The run started; task = runtime context plus the path string; `write_scope None`.
- E-3e variant: the prompt is absent at the read and at `is_tracked_task`, then restored with unapproved content. Same result.
- Consequence: the F4-02 refusal does not apply, because the run is not classified as tracked. A tracked run proceeds without content binding and with project-root write scope; the worker may later read the path through its tools. Unlike F4-02, the directory and FIFO cases need no microsecond race: the path must be non-regular at launch and replaced before the worker reads it.
- Limits: the actor needs write access to `ai/workspace/` at launch (the E-3 threat model). The operator sees a yellow warning, although its wording ("outside ai/workspace/") is wrong. engine-mcp refuses a non-regular path (`server.py:106`); there, only a race between its check and the engine start remains. Gate code from an earlier cycle could plant the path, which DI-06 already covers.
- Origin: tracking based on `isfile` predates iteration 5 and was not tested by the fourth follow-up audit.
- Recommendation: in `main_async`, treat a task whose resolved path lies in `ai/workspace/` as tracked whatever its type, and refuse it with exit 3 when no bytes were read (as engine-mcp does). Correct the warning text. Add a test with a directory at the prompt path.

## 6.0 Observations

No finding is raised for the following.

1. **Read-only state directory (DI-06).** E-1o: a gate that makes `ai/state` read-only defeats both the clear and the `BLOCKED.md` write; the run ends with an exception and `engine_status` reports `shipped: true, blocked: false`. Design DI-06 states that gate code can change any file the operator can, including state files and the engine, so this lies within the accepted limit. Optional hardening: log the unremovable names before writing `BLOCKED.md`, because `log.error` currently follows the write and is skipped when the write fails. Confirm a SHIP with `SHIPPED` and `engine end rc=0` in the log, as the guide states.
2. **macOS.** A directory is now removed with `rmtree`, so the macOS `EPERM` on `unlink` no longer applies. An immutable `.complete` (`chflags uchg`) would end the run BLOCKED with `shipped: true, blocked: true`; overwatch gives BLOCKED precedence. Inference; not tested.
3. **Test coverage.** The BLOCKED path is tested with a stubbed `_remove_state_path`; a real unremovable entry, the `reset_state` return value 1 and the loop-start BLOCKED are not tested (verified by E-1m). The F4-02 engine test covers a file absent at the read only, not a non-regular path (F5-01).
4. **Other `exists` checks.** The prior-SHIP warning in `main_async` (`:2386`), the worker-mode stale `work-complete.txt` removal and the `state_files` list in `engine_status` still use `exists`. They do not affect the verdict or `shipped`; outside this scope.
5. **DI-06.** Unchanged; accepted limit.
