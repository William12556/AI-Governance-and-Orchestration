## 4.0 Findings

### 4.1 Medium

**F3-01 Gate-written state files survive when a gate cannot run.**
- Evidence: the post-gate clear (`orchestrator.py:2040`) follows the UNCHECKED check, which writes `BLOCKED.md` and returns 1 (`:2021-2031`). `run_command_gate` reports UNCHECKED on a timeout, a missing executable or an exception (`gates.py:137-160`). `engine_status` reports `shipped` when `.complete` exists (`server.py:259`).
- Experiment E-1j: a command gate writes `.complete`, `awaiting-approval.md`, `review-result.txt` and `review-feedback.txt`; then either (a) the same gate sleeps past `timeout_seconds`, or (b) a second gate is not runnable. Result in both cases: `rc 1`, `BLOCKED.md` present, and `.complete` (`COMPLETE: iteration 1`), `awaiting-approval.md`, `review-result.txt` and `review-feedback.txt` present. `engine_status` would return `shipped: true` and `blocked: true`.
- Consequence: the engine's status channel reports SHIP for a cycle that ended BLOCKED, through files written by a gate that has exited. Variant (a) is under the worker's control: a worker-written test that sleeps past the gate timeout. `blocked: true`, exit code 1 and the log remain correct, which reduces the risk.
- Documents: engine guide §5.0 ("only the engine's SHIP path leaves `.complete`") and design §6.0 ("do not survive into the verdict or the status") do not hold for this path.
- Recommendation: run the clear immediately after the gate loop, before the UNCHECKED check. Add a test with a gate that writes `.complete` and then times out.

**F3-02 The task file is checked by path and read later by path.**
- Evidence: `main_async` runs the pre-run check at `orchestrator.py:2381` and reads the task at `:2492`. Between them lie log archiving, recipe loading, provider readiness (`await_ready`, up to `readiness.timeout_seconds`, default 60 s) and MCP server start (`:2488`). The content read at `:2492` provides both the task text and the write scope (`:2527`). Nothing compares it with the approved blob hash.
- Experiment E-3: the pre-run check was wrapped so that, after it returned `[]`, (a) a `scratch/` symlink `prompt-U-link.md` pointing at U's approved prompt was re-pointed at work item V's unapproved prompt, or (b) U's approved prompt was edited in place. In both cases the engine passed V's or the edited content to the loop.
- Consequence: unapproved content runs under the work item's approval. Case (b) needs only a file write in the prompt folder during the start-up window. It can also occur without intent, for example when a planner calls `start_engine` and edits the prompt in the next step.
- Origin: the gap exists since the pre-run check (change-ee5357ec). It is not introduced by iteration 3 and was not raised by the earlier audits.
- Recommendation: read the task bytes once, before the pre-run check; verify the realpath rule and that the blob hash of those bytes equals the approved hash of the matched document; use the same bytes for the task and the deliverables. Add a test that changes the file after the check.

## 6.0 Observations

No finding is raised for the following.

1. **engine-mcp checks identity, not approval.** `start_engine` accepts a document of the right work item whose approval no longer matches (added, changed); the started engine then exits 3. This is the iteration 2 design: the approval check is the engine's.
2. **Untracked CLI runs.** A task whose resolved path lies outside `ai/workspace/` runs untracked from the command line with the warning "not tracked", also when the path given names the prompt folder through a directory symlink (E-2l var.). engine-mcp refuses these. Existing CLI design (second follow-up §6.0 note 1).
3. **Benign aliases.** A symlink or directory symlink that resolves to the approved prompt is accepted; the content is the approved file. A hard link to it outside the prompt folder is refused (over-refusal).
4. **Empty name part.** The document pattern changed from `.*` to `.+`; `prompt-<uuid>-.md` is no longer scanned. Not material.
5. **APFS case folding.** Not executed on macOS; behaviour as stated in the second follow-up §6.0 note 1 (inference).
6. **DI-06.** A detached process started by a gate can still write state files after the clear; accepted limit, recorded in the change record.
