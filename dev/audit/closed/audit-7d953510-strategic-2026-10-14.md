## 1.0 Summary

- **Subject:** work item 7d953510, the `api_key_keychain` provider key source. Source commits `9b4cb23` (iteration 1) and `d4c1cdb` (iteration 2); document commits `21b5121`, `8c13a7f`, `f8b300b`, `b7e567b`, `794dfde`. Audited at `origin/main` `794dfde`.
- **Protocol:** P02 Audit (P08 before governance 10.0; Appendix A alias), strategic mode (P02.9.1).
- **Verdict:** accept with remediation. The code implements FR-A to FR-F of the prompt exactly, and no log or exception message can carry the key.
- **Findings:** 0 critical, 0 high, 1 medium, 7 low.
- **Central result:**
  - M-01: the change assumes a Keychain key is safer than an environment key because it never enters a subprocess environment. A gate subprocess can read the item itself through `/usr/bin/security`, so the gate scrubbing guarantee (change-82dbf16a, audit-14e05e35 M-05) does not extend to the Keychain source.
  - L-01: `raise … from None` hides the key-bearing exception from tracebacks but leaves it in `__context__`. No current code path exposes it.
- **Tests:** 322 passed, 1 skipped (root), matching report §8.0. T15 fails against the iteration 1 source and passes after `d4c1cdb`; the auditor confirmed both.
- **Scope gap:** `README.md` v4.2 and `ai/engine/README.md` v2.13, named in the audit request, do not exist at `794dfde` (L-05).

## 4.0 Key Leakage Analysis (NFR-05)

| Path | Result | Evidence |
|---|---|---|
| Log records | No leak | Only `providers.<name>: key source <label>`; label is `env:<VAR>` or `keychain:<service>` |
| ConfigError messages | No leak | Service name, provider name, exit code and constants only; stdout and stderr never interpolated. Probe (d): message omits printed output |
| Orchestrator surface | No leak | `orchestrator.py:2394-2396` prints `str(e)` only |
| Chained `__cause__` | No leak | `from None` on timeout, `OSError` and `UnicodeDecodeError` |
| Implicit `__context__` | Retained in memory | Probes (b) and (c): `err.__context__` is the `UnicodeDecodeError` (`.object` holds the raw bytes) or `TimeoutExpired` (`.output`/`.stdout` hold the output). `traceback.format_exception`, `logging.exception` and `rich.traceback` all honour `__suppress_context__` and omit it. L-01 |
| `security` argv | No leak | argv holds the service name only; the secret returns through a pipe |
| Engine process environment | No leak | Keychain value is returned, never written to `os.environ` |
| Gate subprocesses (pytest and declared command gates) | **Exposed** | M-01 |
| engine-mcp `start_engine` child | No new path | The child reads the Keychain itself; its console output carries ConfigError text only |
| Profile shell commands | Process argv | L-07 |

**M-01 detail.** `_resolve_gate_specs` builds `scrub_env` from `api_key_env` only (`orchestrator.py:2285-2288`). With a Keychain source nothing needs scrubbing, and the change record treats that as the end of the matter ("a Keychain key never enters the environment", out_of_scope item 3). The Keychain item, however, is readable by any process of the same user that runs `/usr/bin/security find-generic-password -s ai-go-mistral -w`, once `/usr/bin/security` is on the item's access list. `mistral_api.md` §4.0 states this for "Always Allow". The auditor also expects (medium confidence) that an item created with `security add-generic-password` without `-T` lists `security` as a trusted application from creation. If so, the documented store command grants this access without any dialog. This can be checked in Keychain Access → item → Access Control.

The worker may write under `tests/` (manifest `writable_paths`), and the pytest gate runs that code as the operator (`gates.py:151-156`). A worker that misbehaves or follows injected content can write a test that runs `security`. The output then enters the gate block (`gates.py:173-177`), which goes to the provider in the next model turn and may reach the run log or state files. Under `api_key_env` the same attack is blocked by scrubbing. Under `api_key_keychain` it is not. This is the same exposure class as audit-14e05e35 M-05 and is rated the same.

## 8.0 Findings

### 8.1 Critical

None.

### 8.2 High

None.

### 8.3 Medium

**M-01. A Keychain-sourced key is readable by gate subprocesses.**
- Location: `ai/engine/src/orchestrator.py:2285-2288` (`scrub_env` from `api_key_env` only); `ai/engine/src/gates.py:151-156, 173-177`; change-7d953510 out_of_scope item 3; design §6.0 gate row.
- Description: see §4.0. Worker-authored test code run by the pytest gate can call `/usr/bin/security` and print the key into the gate block. Environment scrubbing has no Keychain equivalent, so `api_key_keychain` gives weaker isolation from gate code than `api_key_env`. The record states the opposite.
- Recommendation: the operator decides between two options.
  - (a) Accept and document. Record the residual risk in design §3.0/§6.0, the guide §3.0 and the change notes, and correct the out_of_scope rationale.
  - (b) Mitigate. For example, refuse a gate run when any provider uses `api_key_keychain` and the gate output contains a value that matches the resolved key (redaction before the block is built), or run gates in a context without Keychain access.
- Option (b), redacting the resolved key from gate output, is a small engine change and also covers future sources. Its limit is that it catches only verbatim copies.

### 8.4 Low

**L-01. Suppressed context still holds the raw output.**
- Location: `providers.py:419-429`.
- Description: `from None` sets `__suppress_context__` but leaves `__context__` bound to the `TimeoutExpired` or `UnicodeDecodeError` that holds the output (probes b, c). Standard formatters omit it, so nothing leaks today. A future handler that walks `__context__`, or a crash reporter that captures locals, would expose it. The prompt constraint "never … in an exception's … context" is not literally met.
- Recommendation: build the ConfigError inside the `except` block and raise it after the `try` statement, so no context is attached. Add a T6/T15 assertion that `err.__context__ is None`.

**L-02. "Login Keychain" is imprecise.**
- Location: requirements FR-04-07; design §3.0; guide §3.0; `mistral_api.md` §4.0; `providers.py:405`.
- Description: `security find-generic-password` without a keychain argument searches the user's keychain search list, not only the login keychain. Confidence: medium. Verify with `security list-keychains`.
- Recommendation: say "the user's default Keychain search list (normally the login Keychain)", or pass the login keychain path explicitly.

**L-03. Test gaps.**
- Location: `tests/engine/test_providers.py`.
- Description: no Keychain test for `kind: anthropic`, none for an `api_key_env` variable set to `""`, and none on `__context__` (§5.0).
- Recommendation: add the three tests with the L-01 fix.

**L-04. Issue status not advanced.**
- Location: `dev/issue/issue-7d953510-keychain-api-key.md` `status: "open"`.
- Description: P03.7 requires `resolved` when the change is `implemented`.
- Recommendation: set `resolved` with a version-history row.

**L-05. README updates named in scope are absent; README.md contradicts the engine.**
- Location: `README.md` §2.2 and version history; `ai/engine/README.md` §6.0 and version history; commit `b7e567b`.
- Description: `README.md` v4.2 and `ai/engine/README.md` v2.13 are not at `origin/main` `794dfde`. They may be local, unpushed edits. `README.md` §2.2 still marks the Mistral API as *Planned* and requires one oMLX server for both roles, which contradicts FR-04 and this change. `b7e567b` changes table spacing only, has no version-history row and does not use a Conventional Commit message.
- Recommendation: push the intended v4.2 and v2.13 edits and re-check them. They can be verified by document review alone; a follow-up audit is not required (P02.8.2).

**L-06. Design DI-04 guidance is stale.**
- Location: design-14e05e35 DI-04 guidance (2).
- Description: it still prescribes injecting `MISTRAL_API_KEY` per process with a wrapper. `api_key_keychain` supersedes this.
- Recommendation: amend DI-04 to cite change-7d953510.

**L-07. Profile commands place the key in a process argv.**
- Location: `ai/profiles/mistral_api.md:101` (model id check), also step 3.
- Description: the `curl -H "Authorization: Bearer $MISTRAL_API_KEY"` header becomes part of curl's argv, which other local users can see with `ps` while it runs. NFR-05 does not cover process argv, and the pattern predates this change, which carried it forward.
- Recommendation: pass the header through stdin (`curl -H @-` or `--config -`), or accept the risk on a single-user machine and say so.

## 9.0 Positive Findings

- The implementation matches the prompt literally: the resolution order, validation placement, messages, constants, and the specific `UnicodeDecodeError` catch.
- `security` is run from an absolute path with a list argv, no shell, a 10 s timeout and `check=False`. No output reaches any message.
- Each source is read only when configured, so a portable config with `api_key_env` set works on Linux even when `api_key_keychain` is present.
- The resolution runs before any state change (`build_role_bindings` at `orchestrator.py:2393`), so a Keychain failure stops the run cleanly.
- The tests are hermetic and assert the absence of the secret across message, record `msg` and `args`. The `engine_log` fixture prevents vacuous log assertions.
- The report's §6.0 item 2 raised the `UnicodeDecodeError` path proactively, and iteration 2 closed it with a test that fails first.
- The operator documents are accurate and agree with each other and with the code.
