## 4.0 Findings

### 4.1 High

**F2-01 A task file name ending in a newline bypasses the F-02 check.**
- Evidence: `task_document_error` (`stages.py:335`) tests the name with `re.match(r"^prompt-[0-9a-f]{8}-.*\.md$")` (`:346`). `$` also matches before a trailing newline. The scan lists documents with `glob("prompt-*.md")` (`stages.py:199`), which does not match a name ending in `\n`. engine-mcp `_PROMPT_NAME` (`server.py:41`) has the same `$`.
- Experiment E-2g: approved `prompt-<uuid>-work.md` unchanged; new file `prompt-<uuid>-evil.md\n` in `ai/workspace/prompt/`. It is tracked, `prerun_missing` returns `[]`, `main_async` prints "prerequisites for 'implement' met" and proceeds to the provider check; `start_engine` accepts it and launches the engine.
- Consequence: an unapproved document runs under the work item's approval. Only a file write in the prompt folder is needed, which is the H-02 threat model.
- Recommendation: require the resolved task path to be one of the work item's documents for the task stage, as found by the scan (realpath comparison), instead of a separate name test. Use `re.fullmatch` or `\Z` in both name patterns. Add a test with a newline-terminated name.

### 4.2 Medium

**F2-02 The work item is taken from the unresolved task name.**
- Evidence: `work_item` comes from the basename of `args.task` (`orchestrator.py:2264, 2372`). `task_document_error` checks the basename and folder of the *resolved* path. Nothing requires the two names to agree.
- Experiment E-2i: work item U approved; work item V has an unapproved prompt `prompt-V-evil.md` in the prompt folder. A symlink `prompt-U-link.md` in the project root or in `ai/workspace/scratch/` points to it. Result: tracked as U, `prerun_missing` `[]`, `main_async` passes the pre-run check, `start_engine` accepts it. The engine reads V's content and V's declared deliverables. (A link placed inside the prompt folder is refused, because the scan then reports it as an added U document.)
- Consequence: an unapproved prompt runs under another work item's approval.
- Severity rationale: creating a symlink needs more than the write tools of filesystem-mcp, and an actor with a shell can already commit approvals. Hence medium.
- Recommendation: the fix for F2-01 closes this case. Also derive the work item from the resolved name, or refuse when the two names differ. Add a test.

**F2-03 Gate processes can still write `.complete`, which the engine reports as SHIP.**
- Evidence: the review-phase clear (`orchestrator.py:2003`) runs before the gates (`:2006-2024`) and does not include `.complete` or `awaiting-approval.md`. `.complete` is otherwise cleared only at loop start (`:1881`). `engine_status` returns `shipped` = `.complete` exists (`server.py:259`). Governance P10 Option B has the planner report SHIP from `engine_status`; engine guide §5.0 lists `.complete` as the SHIP marker.
- Experiment E-1h: a command gate writes `.complete` (`COMPLETE: iteration 1`), `review-result.txt` and `review-feedback.txt`; the reviewer answers REVISE. Result: `rc 1`, no `SHIPPED` log line, but `.complete` is present, so `engine_status` would return `shipped: true`.
- Consequence: the engine's own status channel can report SHIP for a rejected cycle. This is not DI-06 alone: the engine reads the forged file and reports it. The exit code and log remain correct.
- Recommendation: move the clear of `review-result.txt`, `review-feedback.txt`, `.complete` and `awaiting-approval.md` to after the gates, immediately before the review phase. Add a test with a gate that writes `.complete`. A detached process started by a gate remains DI-06.

## 6.0 Observations

No finding is raised for the following.

1. **Untracked CLI runs.** A task named `Prompt-…`, with an upper-case UUID, or outside `ai/workspace/` runs untracked from the command line, with the warning "not tracked". On a case-insensitive APFS volume, a case variant of the workspace path (`ai/Workspace/…`) would also be untracked, because `realpath` does not normalise case (inference, not executed on APFS). engine-mcp refuses all of these. This is the existing CLI design.
2. **Glob traversal of existing symlinks.** A directory-scoped `replace_text` on an allowed directory could reach a pre-existing symlink under it. The worker has no tool to create symlinks; not tested.
3. **Case folding on Linux.** Protected paths are compared case-folded on all platforms. On a case-sensitive volume this over-refuses only.
4. **Gate-written `BLOCKED.md`.** A gate can make `engine_status` report `blocked`. This can only stop a run (DI-06).
5. **Recipe wording.** `loop-review.yaml` step 5 says "Write your decision"; the OUTPUT section states the verdict is the final response. Not material.
