## 5.0 Key Leakage Analysis (NFR-05)

| Path | Result | Evidence |
|---|---|---|
| Log records | No leak | Unchanged: `providers.<name>: key source <label>` only. T17, T18 assert secret absence across records |
| Exception messages and `args` | No leak | Probes (a) to (f): no message or `args` contains the secret; stdout and stderr are never interpolated |
| `__cause__` | No leak | `None` in every probe |
| `__context__` | No leak | `None` for (b), (c), (f); the non-zero exit and empty paths raise outside any handler. Probe (g): when the caller is itself inside an `except` block, `__context__` is the caller's exception, which is standard Python behaviour and holds no Keychain output; no current caller does this (§4.0) |
| Formatted tracebacks and `logging.exception` | No leak | Probes (b) to (f) |
| `security` argv and engine environment | No change | Service name only in argv; value returned, never written to `os.environ` |
| Traceback frame locals | Pre-existing, not a new path | Probe (d): on a non-zero exit the `_keychain_secret` frame, reachable from the ConfigError's `__traceback__`, holds `result`, whose `stdout`/`stderr` the probe filled with the secret. Unchanged since iteration 1 and outside the four channels the prompt constrains. A real `security` run that exits non-zero prints a diagnostic, not the item, so the practical exposure is negligible; on success the key is in memory by design. Recorded as an observation, not a finding |
| Gate subprocesses | Accepted risk | M-01, accepted (§6.0) |

Iteration 3 adds no new path. It removes the only path the baseline identified (the implicit context).
