## 5.0 Findings

### 5.1 High

**H-01 Worker can forge the reviewer verdict.**
- Evidence: the state directory is in the worker's write scope (FR-05-01, `scope.py:155`). Before the review phase only `work-complete.txt` and `review-feedback.txt` are cleared (`orchestrator.py:1964`). The verdict is read from `review-result.txt` first (`orchestrator.py:2023`). No engine code writes that file, and the reviewer is read-only (`loop-review.yaml`: "You are in read-only mode"). Experiment E-1: a worker that writes `SHIP` into `review-result.txt` while the reviewer answers `REVISE` ends with rc 0 and `.complete`.
- Remaining guards: the read-evidence gate and a failing command gate. A reviewer that read the files and rejected the work is overridden.
- Recommendation: take the verdict from the reviewer's final message only, or clear `review-result.txt` immediately before the review phase. Exclude engine signal files (`review-result.txt`, `.complete`, `BLOCKED.md`, `awaiting-approval.md`, `mcp-run.json`) from the worker scope. Add a test. Correct `guide-engine-operations.md:43` (L-07).

**H-02 Approvals are not bound to document content.**
- Evidence: approvals are `(uuid, stage)` pairs (`stages.py:73-84`); evidence is any `prompt-<uuid>-*.md` (`stages.py:125-144`); the check is set membership (`stages.py:173, 210`). Experiment E-2: after the prompt approval was committed, the prompt was edited (new deliverable) and a second `prompt-<uuid>-second.md` was added, both uncommitted; `prerun_missing` returned `[]`.
- Consequence: a planner with filesystem access only, the case design §8.3 states is protected, can run unapproved content by editing an approved prompt. The ordinary flow "BLOCKED → Return to stage: prompt → revise prompt" also reuses the old approval. DI-03 does not cover this.
- Recommendation: record the git blob hash of each evidence document in the approval entry (`approve.py`), and in the pre-run check require that the committed and working copies still match it, and that no further same-UUID document exists. Document re-approval after a prompt revision in governance (with L-15).

**H-03 Reviewer phase executes write tools.**
- Evidence: the reviewer is offered read-only tools (`orchestrator.py:1042`), but dispatch calls `mcp.call_tool` for any tool the MCP client knows (`orchestrator.py:1222-1239`). The review phase receives no write scope (`orchestrator.py:2003-2016`), so only project-root containment applies. Experiment E-3: a scripted reviewer call `write_file src/x.py` was dispatched.
- Consequence: a hallucinated or plain-text-parsed call can write anywhere in the project, including `ai/config.yaml` (gate commands) and `ai/workspace/` documents. The "read-only reviewer" in the live report (§5.0) describes the tool list only.
- Recommendation: in `run_phase`, refuse any call whose name is not in the offered tool list, and refuse write tools outright in review phases. Add a test.

### 5.2 Medium

**M-01 Write-scope check is fail-open for unrecognised path keys.**
- Evidence: `check` inspects only `PATH_KEYS` and nested `files`/`moves`/`edits` (`scope.py:39-40, 63-73, 174`). A write-classified call with no extracted target is allowed. Experiment E-4: `filename`, `file`, `directory` and `uri` arguments all returned `None` (allowed).
- Inference: the pinned filesystem-mcp 2.5.0 appears to use recognised keys; this was not verified against its schema. Exposure depends on which MCP servers a project configures.
- Recommendation: reject a write-classified call when `scope_targets` returns nothing.

**M-02 Gates other than FAIL do not block completion.**
- Evidence: only `FAIL` overrides SHIP (`orchestrator.py:2112`). `UNCHECKED` (interpreter missing, timeout; `gates.py:155-158`) and an empty gate (no targets resolved from the worker-written summary) let SHIP stand. FR-03-02 states that a stage completes only when all its gates pass; design §6.0 keeps "FAIL overrides SHIP, as today".
- Consequence: a wrong `gates.python` silently disables the pytest gate.
- Recommendation: reconcile requirement and design (amend FR-03-02, or block on `UNCHECKED`). At minimum, list gates that did not pass in `awaiting-approval.md`.

**M-03 Terminology migration incomplete.**
- Evidence: `primer.md:38-46` (both copies, identical) still defines "two domains" with rows `Strategic` and `Tactical`; heading `2.1 Tactical Profiles` (`:11, :76`); "tactical context file" (`:55, :70`); `governance.md:65` "Both domains"; `overwatch.py:564, 576` label "Tactical execution". The V-08 test uses `(Strategic|Tactical) Domains?` and cannot find these.
- Note: audit mode names `strategic`/`tactical` (P02.9, T08 `mode`) are a separate concept and are field values (FR-07-03); whether to rename them is an operator decision.
- Recommendation: rewrite primer §2.0 to the planner/worker/reviewer model; widen the V-08 scan to bare forms with an allowlist for audit modes.

**M-04 Stage scan writes the git index.**
- Evidence: `stages.py:98` runs `git status --porcelain`. Experiment E-5: `.git/index` mtime changed after `git status`, not after `GIT_OPTIONAL_LOCKS=0 git status`. This audit's own `git status` left `index.lock` (§2.0).
- Consequence: `work_status` and the pre-run check are not strictly read-only (FR-08-06, V-12), and a concurrent `approve.py` commit can fail on the lock.
- Recommendation: run git with `--no-optional-locks` (or `GIT_OPTIONAL_LOCKS=0`); add a V-12 test on a git fixture.

**M-05 Provider keys are inherited by gate subprocesses.**
- Evidence: `gates.py:151` calls `subprocess.run` without `env=`, so `MISTRAL_API_KEY`/`ANTHROPIC_API_KEY` reach project tests. `tests/` is worker-writable. Gate output (last 1000 characters) goes into the reviewer prompt, `review-feedback.txt` on FAIL and the debug log.
- Inference: no leak observed (V-09 pass); the path exists.
- Recommendation: remove every configured `api_key_env` variable from the gate environment; extend V-09 to committed files.
